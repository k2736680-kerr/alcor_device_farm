1. 需求概述
需求介绍
当前测试条目、数据集、质量评估和性能压测的管理前端位于 altair-ai-hub。由于功能多次迭代，新增、编辑、导入和任务创建中出现了大量历史字段、重复配置和页面职责混杂的问题。
本次将测试管理能力整体迁移至 llm-eval：新建独立 Eval Console 前端、新 API 和新数据库模型；现有历史数据从当前 llm-eval PostgreSQL 与本机文件目录一次性迁入新库。新平台不再兼容旧前端、旧接口和旧字段格式。
核心内容

以 HTTP、SSE、WebSocket 协议为基础，通过可配置场景模板录入用例；新增同协议业务场景不需要改前端或执行器代码
高效组织和复用测试数据

本期范围
1. 在 llm-eval 中新建 Eval Console 前端。
2. 在 eval_server 中新建 /api/v1、Run、Worker 和统一结果模型。
3. 支持 HTTP、SSE、WebSocket 协议执行；ASR、QA 流式等仅作为协议模板，不作为硬编码业务类型。

本期不做
1. 不维护新旧系统双读、双写或在线格式兼容。
2. 不引入 Redis、Kafka、Temporal、对象存储集群。

6. 不将 WeData-Log 的全量历史日志复制到本平台；仅查询运行时间窗内的关联日志与聚合指标，并保存引用、摘要和必要的脱敏片段。

3. 核心流程
3.1 用例与数据集维护
1. 用户通过钉钉登录 Eval Console。
2. 用户进入“用例库”，选择 HTTP、SSE 或 WebSocket 协议下的场景模板。
3. 用户填写当前模板所需字段；前端根据服务端下发的 JSON Schema 渲染表单，服务端执行协议和敏感字段校验。
4. 服务端保存标准化 Case 元数据，明细写入 ClickHouse，并记录创建人、最后修改人和审计日志。
5. 用户在“数据集”中添加已有用例，或通过导入向导批量创建用例。
6. 数据集发生变更时增加不可变版本；对应 Case 明细按版本写入 ClickHouse，后续运行固定引用版本与选择规则。
数据流
用户填写模板
  → Case 校验并保存
  → 选择/导入 Case
  → 编排 Dataset
  → 增加 Dataset 版本并写入 ClickHouse
  → 供 Run 创建可复现的选择快照使用

3.2 导入
1. 用户选择协议场景模板，上传 CSV/XLSX；WebSocket 音频等场景可上传媒体 ZIP。
2. 服务端创建导入会话并读取列名、样例数据。
3. 用户确认字段映射和样例预览。
4. 服务端校验必填项、JSON、媒体匹配、重复项和敏感字段。
5. 用户选择全量导入或将该批数据作为大数据集版本写入 ClickHouse。
6. 用户确认导入后，服务端分批写入 Case 元数据与 ClickHouse 明细。
7. 页面展示成功数、失败数、总行数和可用抽样比例，并支持下载错误行文件。
3.3 运行创建与执行
1. 用户从数据集详情或运行中心发起运行。
2. 用户选择运行类型、Target、运行配置（Config）、标签筛选和数据选择策略：全量、固定条数、20%/30% 等比例抽样或分层抽样。
3. 系统展示总数据量、选中样本数、抽样 seed、预计时长、并发限制和运行参数。
4. API 记录发起人，校验 Target 的最大并发和最大时长；将数据集版本、选择规则和 seed 固化为 Run 快照。
5. Worker 通过 PostgreSQL 租约领取 Run，从 ClickHouse 分页流式读取选中 Case，并读取 YAML 中的密钥引用。
6. Worker 根据 Case 的 protocol 调用 HTTP、SSE 或 WebSocket Protocol Executor；质量评分仅在需要时作为后置步骤执行。
7. Worker 持续写入运行事件、进度、结果和制品索引；用例级结果批量写入 ClickHouse。
8. Worker 根据运行时间窗、Target 的观测配置及 X-Eval-Run-Id / traceparent 等关联标识，通过 HyperDX MCP 查询 WeData-Log 和监控数据。
9. 用户在运行详情查看状态、指标、失败用例、目标服务 CPU/内存/实例数、关联日志、报告和日志。
控制流
创建 Run
  → queued
  → preparing
  → running
  → passed / failed / canceled / timeout / infra_failed

3.4 可观测性关联流程
1. 系统在 config.yaml 中维护 Target 到 WeData 服务标识、HyperDX MCP 连接、日志字段和指标模板的映射；用户不配置、不选择观测服务。
2. 指标查询规则属于系统 Template，例如 CPU utilization、内存、实例数、请求量、错误率和 P95；模板由部署/平台管理员维护。
3. Worker 在发起请求时注入 X-Eval-Run-Id、X-Eval-Attempt-Id 和 W3C traceparent；目标服务若支持，将这些字段写入日志或 Trace。
4. Worker 记录运行开始、结束和预热/冷却时间窗，并通过 HyperDX MCP 查询该时间窗内的 WeData-Log 和监控指标。
5. 系统优先按 Run ID / Trace ID 关联日志；目标系统不支持关联字段时，降级按系统配置的服务、实例、时间窗和接口路径查询。
6. 系统只保存指标聚合、HyperDX 查询条件、日志引用与限量脱敏异常片段；原始日志仍由 WeData-Log 管理。
默认采集目标服务 CPU utilization、内存使用率、实例/Pod 数、请求量、错误率、P95 时延和限流/异常日志数量；同时采集 Worker CPU、内存、网络，防止将发压端饱和误判为目标服务瓶颈。
3.5 LLM 动态报告生成
1. Worker 完成运行后，自动保存标准 RunResult、原始 Locust/评估器报告和脱敏失败摘要。
2. 系统自动创建报告生成后置任务；前端不调用生成接口。
3. 报告服务根据 Run 的 report_template_version 组装结构化输入：运行信息、核心指标、门禁结果、错误分布、目标服务资源曲线、关联日志摘要和受限数量的脱敏样本。
4. 报告服务调用配置的 LLM，生成“结论、性能变化、资源瓶颈证据、日志异常归因、与阈值对比、建议动作”等 Markdown 内容。
5. 系统将 Markdown 渲染为 HTML，并作为独立 Artifact 保存；同时记录模型、模板版本、输入 hash 和生成时间。
6. LLM 生成失败或超时时，保留确定性基础报告，Run 的通过/失败状态不受影响；报告状态标记为 failed，由平台后台按策略重试。
LLM 只用于报告解释，不能改变断言、门禁和运行状态；请求 Header、Cookie、密钥、完整响应体和超限日志必须在送入 LLM 前脱敏或截断。
3.6 历史数据迁移与切换
1. 在预生产环境盘点当前 llm-eval PostgreSQL 和本地目录。
2. 配置旧 URL origin 到新 Target 的映射，配置需要人工绑定的密钥引用。
3. 执行一次完整迁移演练，核对数据条目、数据集关联、报告、日志和媒体 hash。
4. 切换窗口开始后停止旧评估页面写入。
5. 执行最终迁移和校验，生成迁移报告。
6. 发布 Eval Console，所有新写入进入新库。
7. 删除 Altair 的旧评估管理页面和旧接口。
4. 详细设计
接口设计
前端仅调用 /api/v1。统一响应结构：
{
  "request_id": "req_01J...",
  "data": {},
  "error": null
}

REST 路径约定
● 所有资源路径使用复数名词：/cases、/datasets、/runs、/templates、/case-imports；
● POST /api/v1/cases 表示在 Case 集合中创建一个 Case，因此使用复数是 REST 规范；单个资源使用 /api/v1/cases/:id；
● 用例导入是独立资源，命名为 /case-imports，避免通用 /imports 无法看出导入对象；
● 取消、重试和报告生成也建模为子资源：cancellations、attempts、reports，不使用动词型路径；
● 抽样是 Run 的创建参数，不单独暴露“预览接口”。数据集统计接口返回总量和分布；Run 创建后保存最终选中数、selection 和 seed。

{
  "run_kind": "performance",
  "dataset_id": "ds_01JABCD",

Case 数据结构
type Protocol = 'http' | 'sse' | 'websocket';

interface Case {
  id: string;
  protocol: Protocol;
  templateId: string;
  schemaVersion: number;
  name: string;

  tags: string[];

  spec: Record<string, unknown>;
  createdBy: ActorSnapshot;
  updatedBy: ActorSnapshot;
  createdAt: string;
  updatedAt: string;
}

Case 以协议而非业务名称建模：ASR 是 WebSocket 场景模板，QA 流式是 SSE 场景模板，普通 API 是 HTTP 场景模板。模板以 JSON Schema 和默认配置存储，新增同协议业务场景只需新增模板，无需修改前端或 Worker 代码。
Case 只保存相对路径、请求/连接定义、消息帧或媒体节奏和断言；host、环境和密钥不属于 Case，而由 Target 在运行时提供。

WeData 与 HyperDX MCP 的连接不暴露为用户配置接口，部署时在 config.yaml 维护：
observability:
  hyperdx_mcp:
    endpoint: ${HYPERDX_MCP_ENDPOINT}
    token_ref: hyperdx_mcp_token
  services:
    payment-api:
      wedata_service: payment-api-prod
      correlation_fields: [x_eval_run_id, trace_id]
      metric_templates: [runtime-default]
      log_template: service-errors
  metric_templates:
    runtime-default:
      metrics: [cpu_utilization, memory_utilization, pod_count, request_rate, error_rate, p95_latency]

Target 仅保存 service_key=payment-api；Worker 使用该 key 读取系统配置、调用 HyperDX MCP。这样用户只需选择 Target 与 Config，日志服务、指标查询与字段映射由平台统一维护。
Supabase Storage 制品设计
首期使用 Supabase Storage，按稳定对象 Key 保存，避免依赖本机磁盘：
Bucket: eval-media
  media/{sha256-prefix}/{sha256}-{filename}

Bucket: eval-artifacts
  snapshots/{snapshot-id}/cases.jsonl
  runs/{run-id}/attempts/{attempt-id}/report.html
  runs/{run-id}/attempts/{attempt-id}/metrics.json
  runs/{run-id}/attempts/{attempt-id}/task.log
  runs/{run-id}/attempts/{attempt-id}/reports/{report-id}.html

● API 为浏览器导入和 Worker 上传签发短期上传 URL；浏览器与 Worker 不持有 Supabase 管理员密钥。
● 数据库仅保存 bucket + object_key + sha256 + size + content_type，不保存可变的公开 URL。
● Worker 运行时将需要的媒体下载到临时缓存目录，完成后清理；报告和日志直接上传至 eval-artifacts。
● 通过 ArtifactStore 接口隔离 Supabase 实现；未来迁移 S3 时保留 object key 和元数据，仅替换存储适配器并批量复制对象。
历史数据迁移设计
迁移 CLI
迁移命令位于 eval_server/cmd/migrate_legacy_eval：
migrate-legacy-eval inventory  --source-dsn <old> --media-source <old-dir>
migrate-legacy-eval plan       --state-file migration-state.sqlite --target-map targets.yaml
migrate-legacy-eval apply      --state-file migration-state.sqlite --target-dsn <new> --clickhouse-dsn <new> --storage-config <supabase.yaml> --resume
migrate-legacy-eval verify     --state-file migration-state.sqlite --report migration-report.json
migrate-legacy-eval rollback   --state-file migration-state.sqlite

migration-state.sqlite 位于迁移执行机，只用于断点续跑和临时维护“旧 ID → 新 ID”的导入关系；不会部署到线上，也不会写入新业务数据库。新数据库只保存新主键和正常外键关系。
